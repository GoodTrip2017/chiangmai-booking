# 預約管理與分析整合紀錄

## 現有功能與資料

- 預約以 PostgreSQL `bookings` 保存；`date`、`slot` 是清邁當地牆上時間，`created_at` 是 UTC 時間戳。
- 公開預約預設直接確認；資料庫交易與日期鎖會檢查重疊時段，12 人容量不可超賣。`request_key` 防止同一次送出重複建單。
- 後台保留原管理密碼，並新增管理員、門市人員與唯讀分析帳號；雜湊 Cookie 工作階段與同源 CSRF 驗證保護所有操作。
- Resend 確認信與 LINE 工作群組推播已連線。現有 LINE webhook 只辨識工作群組，不代表客人已綁定 LINE。
- 舊欄位 `referral` 是選項文字，`source` 是預約入口；歷史資料沒有實際到店人數、完整狀態歷程或通知發送紀錄。

## 資料模型與遷移原則

- 保留原始 `bookings.id`、`created_at`、`date`、`slot`、聯絡資料、舊 `referral` 與 `line_user_id`；只加欄位與新表，不刪除或重寫舊預約。
- 得知管道改用穩定 ID；舊選項保留為獨立的歷史 ID，不能把模糊的「網路搜尋」猜成 Google 搜尋。
- 目前以標準化 Email 建立顧客 ID；舊 `line_user_id` 原樣保留，但尚未有可驗證的客人 LINE 綁定流程，不用 LINE 聯絡欄位推測身分。絕不只依姓名合併。歷史無法確認的到店結果保持未知。
- 預約入口、客人自述得知管道、可辨識的首次追蹤來源分開保存。對沒有資料的歷史預約顯示「未知」。
- 操作、狀態、通知均記錄事件與時間；統計查詢使用清邁日期基準，改期只計入同一筆預約一次。
- 新資料結構先在隔離測試庫執行重複遷移與舊資料驗證，再部署；正式資料庫備份與復原狀態在切換前重新檢查。

## 已確認營運決策

- 公開預約維持自動確認，容量成功鎖定後才回覆「已確認」。
- LINE 預約通知先只發至已驗證的工作群組；客人 LINE 綁定未建立前不得宣稱客人收到 LINE 通知。
- 固定規則起點為 14:00–23:00、週二公休、90 分鐘服務、14:00 起始與同時接待 12 人；完整服務必須在營業結束前完成。

## 指標口徑

- 預約筆數：符合篩選條件的不同 `bookings.id` 數。
- 預約人數：同一批預約的 `pax` 總和；取消與未到需依各報表明確列入或排除。
- 實際到店人數：有效報到事件所確認的 `actual_pax` 總和；未報到為未知而不是零。
- 完成到店筆數：有有效報到、未撤銷的預約數；`CHECKED_IN` 轉 `COMPLETED` 不重複計數。
- 已完成預約：狀態為 `COMPLETED` 的預約數。
- 到店日期與建立日期分別以 `date` 及清邁時區轉換的 `created_at` 計算；報表會顯示使用哪個日期。
- 取消率：已到期且結果明確的取消預約 ÷ 已到期且結果明確的報到、完成、取消及未到預約。
- 未到率：已到期且結果明確的未到預約 ÷ 已到期且結果明確的報到、完成及未到預約；取消不列入分母。
- 來源占比：該來源預約筆數 ÷ 所有符合篩選條件的預約筆數。來源取消率及未到率沿用總表的已到期分母規則。
- 30／60／90 天回訪率：在可追溯期間首次記錄報到後，於指定天數內再次報到的 Email 聯絡人 ÷ 已有完整指定天數觀察期的首次記錄到店聯絡人。這不是所有同行者的回訪率，也不證明真實首次到店。
- 「既往到店紀錄」篩選以這筆預約到店日之前、同一 Email 聯絡人的有效報到為準；「此前無到店紀錄」不代表真正的新客。同日多筆預約不會互相視為回訪，無法辨識聯絡人的舊資料獨立列出。
- 比率提供分子、分母；零分母顯示「—」，歷史無資料顯示「未知」。

## 已實作的管理流程

- 管理員可編輯營業日、時間、服務長度、開始間隔、12 人以內同時容量，以及日期／時段例外；影響現有預約時先列出預約，不會自動取消。
- 預約清單、週曆、今日營運、詳情、顧客記錄、來源與追蹤連結、趨勢及回訪分析均由資料庫查詢；管理員可匯出目前篩選的 CSV，試算表公式欄位會轉為文字。
- 預約資料與狀態變更檢查版本並保存修改原因、操作者及前後資料。已結案狀態的更正由管理員操作並重新檢查容量。超出原預約人數的報到也限管理員核准。
- LINE 僅通知工作群組。確認、修改、取消及行前提醒有中英文範本與預覽；通知寫入排程／嘗試／API 接受或失敗紀錄。改期、取消、報到與未到會移除舊提醒。管理員可預覽對象與內容後受控重送。
- 管理設定、帳號、追蹤來源與個資 CSV 匯出記錄於 `system_events`；預約內異動另存 `booking_events`。

## 仍需完成或驗證

- 尚無客人 LINE 帳號綁定與私訊，因此不能推斷客人已收到 LINE；LINE API 接受也不是實際送達或已讀。
- 舊預約缺少來源、實際到店人數及歷史容量快照時，不能補造數值。完整歷史容量使用率、匿名預約漏斗與營收指標目前不能可靠計算。
- 目前顧客按 Email 識別，沒有人工合併流程；跨 Email 或同行者無法自動識別為同一人。
- 正式上線前須核對 Railway 備份可還原、執行最新草稿 PR 的完整 CI、在備份後進行遷移與正式環境抽查。草稿 PR 尚未合併到自動部署的正式分支。

## 發布界線

此分支是隔離開發，不直接自動部署。完成資料遷移、功能、權限、安全與統計驗證後才合併到正式分支。
