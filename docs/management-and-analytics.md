# 預約管理與分析整合紀錄

## 現有功能與資料

- 預約以 PostgreSQL `bookings` 保存；`date`、`slot` 是清邁當地牆上時間，`created_at` 是 UTC 時間戳。
- 公開預約預設直接確認；資料庫交易與日期鎖會檢查重疊時段，12 人容量不可超賣。`request_key` 防止同一次送出重複建單。
- 後台以單一管理密碼、雜湊 Cookie 工作階段與同源 CSRF 驗證保護；已有週曆、新增、修改、取消、重寄 Email。
- Resend 確認信與 LINE 工作群組推播已連線。現有 LINE webhook 只辨識工作群組，不代表客人已綁定 LINE。
- 舊欄位 `referral` 是選項文字，`source` 是預約入口；歷史資料沒有實際到店人數、完整狀態歷程或通知發送紀錄。

## 資料模型與遷移原則

- 保留原始 `bookings.id`、`created_at`、`date`、`slot`、聯絡資料、舊 `referral` 與 `line_user_id`；只加欄位與新表，不刪除或重寫舊預約。
- 得知管道改用穩定 ID；舊選項保留為獨立的歷史 ID，不能把模糊的「網路搜尋」猜成 Google 搜尋。
- 顧客識別優先使用既有 LINE 使用者 ID，其次用標準化 Email；絕不只依姓名合併。歷史無法確認的到店結果保持未知。
- 預約入口、客人自述得知管道、可辨識的首次追蹤來源分開保存。對沒有資料的歷史預約顯示「未知」。
- 操作、狀態、通知均記錄事件與時間；統計查詢使用清邁日期基準，改期只計入同一筆預約一次。
- 新資料結構先在隔離測試庫執行重複遷移與舊資料驗證，再部署；正式資料庫備份與復原狀態在切換前重新檢查。

## 已確認營運決策

- 公開預約維持自動確認，容量成功鎖定後才回覆「已確認」。
- LINE 預約通知先只發至已驗證的工作群組；客人 LINE 綁定未建立前不得宣稱客人收到 LINE 通知。
- 固定規則起點為 14:00–23:00、週二公休、90 分鐘服務、14:00 起始與同時接待 12 人；完整服務必須在營業結束前完成。

## 指標口徑

- 預約筆數：符合篩選條件的不同 `bookings.id` 數。
- 預約人數：同一批預約的 `pax` 總和；取消與未到需依各報表明確列入或排除。
- 實際到店人數：有效報到事件所確認的 `actual_pax` 總和；未報到為未知而不是零。
- 完成到店筆數：有有效報到、未撤銷的預約數；`CHECKED_IN` 轉 `COMPLETED` 不重複計數。
- 已完成預約：狀態為 `COMPLETED` 的預約數。
- 到店日期與建立日期分別以 `date` 及清邁時區轉換的 `created_at` 計算；報表會顯示使用哪個日期。
- 比率提供分子、分母；零分母顯示「—」，歷史無資料顯示「未知」。

## 發布界線

此分支是隔離開發，不直接自動部署。完成資料遷移、功能、權限、安全與統計驗證後才合併到正式分支。
